# NagramXF「平板优化模式」完整开发方案

> **项目代号：** Enhanced Tablet Mode\
> **中文名称：** 平板优化模式\
> **开发基线：** NagramXF `dev` 分支\
> **代码策略：** 增量改造，独立功能模块 + 功能开关\
> **第一版范围：**
> 完整实施导航优化、搜索/评论状态恢复、媒体手势适配及平板兼容性\
> **文档性质：** 需求说明、源码审计结论、技术设计、实施计划与验收标准

------------------------------------------------------------------------

## 1. 项目背景

NagramXF
目前已有手机布局和平板双栏布局。用户希望在保留现有手机模式及原版平板模式的前提下，增加一个独立的「平板优化模式」，重点改善平板上的返回导航和全屏媒体操作体验。

本项目不是重新开发平板客户端，也不是复制整套平板源码，而是在现有
Telegram
页面体系上增加导航协调、状态恢复和媒体系统手势安全区域适配能力。

### 1.1 已确认的开发决策

  项目           决策
  -------------- -------------------------------------------------------
  源码基线       NagramXF `dev` 分支
  代码隔离方式   增量改造，不复制整套平板实现
  第一版范围     完整实施全部规划功能
  原版平板模式   保留，关闭优化开关时继续使用原逻辑
  手机模式       不改变原有行为
  系统导航方式   Android 手势导航模式（底部横线、上滑回桌面/切换应用）
  手势策略       不屏蔽系统 Home / Quick Switch 手势，采用安全区域避让

## 2. 用户遇到的问题及需要解决的问题

本项目首先要解决以下真实使用问题。

### 问题一：平板上搜索结果、评论和视频之间无法按预期逐级返回

用户实际操作流程：

1.  打开一个频道。
2.  在频道内搜索关键词。
3.  浏览搜索结果。
4.  打开某条消息的评论。
5.  浏览评论内容。
6.  播放评论区中的视频。
7.  使用 Android 屏幕左边缘右滑返回。

**当前问题：**
从评论页面或评论区视频返回时，不能稳定地回到之前的搜索结果界面。可能出现返回层级不符合用户操作顺序、搜索结果界面没有恢复，或返回后落到频道消息列表等情况。

**期望行为：**

``` text
聊天列表
  ↓
频道
  ↓
搜索结果
  ↓
评论页面
  ↓
评论区视频
  ↓ 左滑返回
评论页面
  ↓ 左滑返回
原搜索结果（关键词、位置均保留）
  ↓ 左滑返回
频道消息列表
  ↓ 左滑返回
聊天列表
```

要求：

-   返回顺序与进入顺序一致。
-   视频退出后回到原评论页面。
-   评论退出后回到原搜索结果。
-   搜索关键词、筛选条件、当前结果和滚动位置尽可能保留。
-   不因返回操作重新创建父级频道页面。
-   不重复发起不必要的搜索请求。
-   不出现一次手势关闭多个页面的情况。

### 问题二：平板多栏布局下，系统返回事件与应用内部导航协调不一致

NagramXF
的平板布局并非单一页面栈，而是由多个导航容器共同管理。系统左边缘返回最终进入
Activity
的返回分发逻辑，再由应用决定当前应该关闭哪个页面或处理哪个内部状态。

用户希望左边缘右滑的行为符合直观的页面层级：先关闭当前媒体界面，再返回评论，再恢复搜索结果，而不是直接退出频道或丢失搜索上下文。

**需要解决：**

-   统一平板不同导航容器的返回分发规则。
-   保留原有 Android 系统返回手势。
-   协调覆盖层、右侧页面、媒体查看器和 ChatActivity 内部状态。
-   避免返回事件被多个容器重复消费。
-   顶部返回按钮与系统返回手势遵循一致的页面状态优先级。

### 问题三：全屏视频进度条与 Android 底部系统手势冲突

用户使用的是 **Android
手势导航模式**，屏幕底部有系统手势横线。全屏播放视频时，底部进度条靠近系统手势区域。

**当前问题：** 手指拖动进度条时，系统可能将靠近屏幕底部的滑动识别为 Home
/ Quick Switch 手势，导致误返回桌面或触发应用切换，影响进度拖动。

**期望行为：**

-   全屏视频进度条及控制栏避开系统底部强制手势区域。
-   横屏、竖屏均能正确计算安全距离。
-   进度条在安全区域内具有足够大的触摸热区。
-   系统上滑回桌面、应用切换仍然正常。
-   退出全屏后恢复原有布局。
-   不改变视频画面缩放比例和播放内核。

### 问题四：优化不能破坏现有手机模式和原版平板模式

用户希望新功能独立、可控、可回退。

**需要解决：**

-   增加独立的「平板优化模式」开关。
-   原版平板模式继续保留。
-   手机模式保持原有行为。
-   新逻辑仅在平板布局且开关启用时生效。
-   关闭优化模式后，不残留临时导航状态。
-   尽量减少对 Telegram 核心业务类的修改，便于同步上游更新。

## 3. 项目目标与非目标

### 3.1 项目目标

1.  增加 Enhanced Tablet Mode 独立开关。
2.  优化平板系统返回事件的统一分发。
3.  修复搜索结果 → 评论 → 视频的逐级返回体验。
4.  恢复搜索关键词、结果位置和必要上下文。
5.  解决 PhotoViewer 全屏视频控制栏与底部系统手势区域冲突。
6.  适配平板横屏、竖屏及窗口尺寸变化。
7.  确保手机模式和原版平板模式不受影响。
8.  建立调试日志和完整回归测试。

### 3.2 非目标

第一版不做以下事情：

-   不复制 `LaunchActivity`、`ChatActivity`、`ActionBarLayout`
    等大型类。
-   不重写 Telegram 的 Fragment 管理体系。
-   不建立与 Telegram 原有 Fragment 栈并行的完整页面栈。
-   不修改消息收发、服务器搜索和数据库业务。
-   不更换视频播放内核。
-   不禁用或拦截 Android Home / Quick Switch 系统手势。
-   不改变手机模式的页面布局和手势逻辑。
-   不重新设计平板双栏 UI。

## 4. 模式设计与功能隔离

### 4.1 三种使用模式

  ----------------------------------------------------------------------------------
  模式                    布局                    导航及媒体逻辑
  ----------------------- ----------------------- ----------------------------------
  手机模式                原有手机单栏布局        原有逻辑

  原版平板模式            原有平板双栏布局        原有逻辑

  平板优化模式            继承原有平板双栏布局    启用新的返回协调、状态恢复和媒体
                                                  Insets 适配
  ----------------------------------------------------------------------------------

建议配置名称：

-   中文：平板优化模式
-   英文：Enhanced Tablet Mode
-   配置键：`tabletOptimizedMode`

建议第一版默认关闭，避免升级后自动改变用户现有行为。用户主动开启后才应用新逻辑。

### 4.2 模式判断原则

必须区分两个概念：

1.  设备/窗口是否使用平板布局。
2.  用户是否启用平板优化导航。

不能把 `AndroidUtilities.isTablet()`
全局替换成优化模式判断。该方法可能被布局、弹窗、窗口和其他功能共同使用，改变它可能产生大范围副作用。

优化逻辑应通过独立判断控制：

``` java
TabletModeManager.shouldApplyEnhancedMode()
```

该方法的实际实现应接入项目已有配置机制，并结合当前平板布局状态判断。

### 4.3 配置存储

-   使用项目已有 SharedPreferences / 配置体系。
-   不写入聊天数据库。
-   不与账号消息数据耦合。
-   关闭模式时清理临时状态快照。
-   切换模式不能强制销毁当前媒体播放实例。

## 5. 源码审计结论与待核验事项

> 说明：此前针对 `dev` 分支的审计已定位核心文件和关键方法，但尚未固定
> Git commit
> SHA，也未完成所有调用链的逐行验证。因此本节区分「已发现的源码结构」与「正式编码前必须再次核验的事项」。不得把待核验假设直接当成最终
> Bug 根因。

### 5.1 已发现的平板导航架构

`LaunchActivity` 管理多个导航容器，主要包括：

-   `actionBarLayout`：主导航。
-   `rightActionBarLayout`：平板右侧导航。
-   `layersActionBarLayout`：覆盖层导航。

这些容器及其 Fragment 栈共同构成平板导航结构。

**结论：** 应保留现有布局和 Fragment
栈。新功能负责协调返回和保存内部页面状态，不另建一套完整页面栈。

### 5.2 已发现的返回分发差异

审计中发现 `LaunchActivity.onBackPressed()`
的平板分支对不同容器采用了不同处理方式：

-   主导航调用 `actionBarLayout.onBackPressed()`。
-   覆盖层调用 `layersActionBarLayout.onBackPressed()`。
-   右侧导航分支曾直接获取栈顶 Fragment，调用其
    `onBackPressed(true)`，再调用 `finishFragment()`。

而 `ActionBarLayout.onBackPressed()` 还可能处理
GroupCall、SheetFragment、ActionBar 搜索框等内部状态。

这说明右侧分支与完整 `ActionBarLayout`
返回流程并不完全等价，是优先审查和测试的位置。

**修改原则：** 不应未经验证就机械地把右侧分支替换成某个方法。需要检查
`sheetFragment`、覆盖层、媒体查看器及 Fragment
生命周期，再决定统一分发的具体实现。

### 5.3 Android 左边缘返回手势已经存在

源码中已有 Android 13+ `OnBackInvokedCallback` 和 Android 14+
`OnBackAnimationCallback` 相关处理；平板路径会进入 Activity 返回处理。

`ActionBarLayout` 另有应用内部 Fragment 滑动返回实现。

这两套机制不同：

-   Android 系统边缘手势：系统触发 Back 回调。
-   `ActionBarLayout` 内部滑动：应用自己的触摸导航。

**结论：** 第一版不重写手势识别，不修改系统返回手势本身，重点修复 Back
事件进入应用后的分发和页面状态恢复。

### 5.4 搜索结果属于 ChatActivity 内部状态

审计发现 `ChatActivity` 内部有搜索结果列表容器及显示状态管理，例如：

-   `isMessagesSearchListVisible()`
-   `showMessagesSearchListView(boolean)`
-   `onBackPressed(boolean)`

搜索结果不是独立 Fragment，而是 ChatActivity 内部管理的界面状态。

**结论：** 搜索状态恢复应该围绕原有 ChatActivity
实例进行，不应重新创建一份搜索页面。

### 5.5 评论页面通过 ChatActivity 进入导航体系

审计发现评论入口涉及：

-   `didPressCommentButton()`
-   `openDiscussionMessageChat()`
-   `processLoadedDiscussionMessage()`

讨论/评论页面会创建新的 `ChatActivity` 实例，并通过
`presentFragment(chatActivity)` 进入现有导航体系。

这意味着父级 ChatActivity 理论上可以保留在导航栈中。

**待核验：**
搜索结果点击消息时，是否提前隐藏搜索结果容器；打开评论前后搜索列表可见状态是否发生变化；父级页面恢复时是否需要重新布局或加载。

因此不能仅凭目前代码结构断言搜索恢复失败的唯一根因。

### 5.6 PhotoViewer 全屏窗口与 Insets

审计发现 `PhotoViewer` 自己管理全屏窗口及容器，并通过
`WindowInsetsCompat` 处理窗口 Insets。

现有处理主要关注系统栏和显示缺口，并存在全屏隐藏导航栏后允许视频使用底部空间的设计。

对于 Android 手势导航，系统导航栏隐藏时，`systemBars()`
的底部值可能不足以表达仍然存在的强制系统手势区域。

**结论：** 应在 PhotoViewer 的 Insets 处理中单独考虑
`mandatorySystemGestures()`，并只调整视频控制栏，不改变视频画面本身的尺寸和缩放。

### 5.7 视频控制栏与进度条

审计发现 `PhotoViewer` 中有
`createVideoControlsInterface()`，视频控制栏以底部对齐方式加入全屏容器。控制栏触摸处理会把事件交给
`VideoPlayerSeekBar`。

进度条本身已有按下、移动、松开处理。

**结论：**
第一优先级是将控制栏从底部强制手势区域上移，而不是重写进度条触摸算法。若实机测试仍有触摸问题，再对热区进行小范围调整。

### 5.8 正式编码前必须补全的审计

1.  固定 `dev` 分支 commit SHA。
2.  确认搜索结果列表点击消息的具体回调。
3.  确认搜索结果点击后是否调用隐藏搜索列表的方法。
4.  确认评论页面实际使用的导航容器和 Fragment 栈。
5.  确认 `presentFragment()` 对父子页面的生命周期处理。
6.  确认 PhotoViewer 全屏窗口的 Insets 监听是否覆盖所有 Android 版本。
7.  确认项目 `compileSdk`、`minSdk`、AndroidX Core 版本。
8.  确认 `SettingsActivity` 中实际设置项构建方法及配置保存方式。
9.  检查 PhotoViewer 的 `videoPlayerControlFrameLayout` 和
    `videoPreviewFrame` 是否共用相同的底部定位逻辑。
10. 在真实平板或可复现的手势导航环境下记录现状。

## 6. 目标架构

建议新增独立包：

``` text
TMessagesProj/src/main/java/org/telegram/ui/tablet/
├── TabletModeManager.java
├── TabletBackDispatcher.java
├── TabletStateManager.java
├── TabletSearchState.java
├── TabletMediaInsetsController.java
└── TabletDebugLogger.java
```

### 6.1 TabletModeManager

职责：

-   读取和保存优化模式配置。
-   判断当前是否处于平板布局。
-   判断优化模式是否生效。
-   在手机模式下阻止优化逻辑误运行。
-   模式切换时清理临时状态。

### 6.2 TabletBackDispatcher

职责：

-   统一优化模式下的平板 Back 事件分发。
-   判断媒体查看器、覆盖层、Sheet、当前 Fragment 和内部页面状态。
-   防止同一次返回事件被多个导航容器重复消费。
-   在没有可处理的优化状态时回退到原有导航机制。
-   让系统返回和顶部返回按钮遵循一致的页面优先级。

该类不负责识别手指是否从屏幕边缘滑入；系统手势仍由 Android
原生机制触发。

### 6.3 TabletStateManager

职责：

-   保存从搜索结果进入评论前的必要上下文。
-   判断返回的是否是原始父级 ChatActivity。
-   在父页面恢复后按需恢复搜索状态。
-   避免重复搜索请求。
-   处理消息删除、搜索结果变化和页面销毁。

### 6.4 TabletSearchState

建议保存：

``` java
class TabletSearchState {
    long dialogId;
    String query;
    long selectedMessageId;
    int firstVisiblePosition;
    int firstVisibleOffset;
    boolean searchListVisible;
    // 其他经过源码核验确实需要的搜索过滤条件
}
```

要求：

-   以消息 ID 作为恢复定位的主要依据。
-   RecyclerView position 和 offset 作为辅助。
-   不能仅依赖列表第几项，因为搜索结果更新后位置可能改变。
-   不保存不必要的大对象或整个消息列表副本。

### 6.5 TabletMediaInsetsController

职责：

-   读取系统手势区域和系统导航栏 Insets。
-   计算媒体控制栏的安全底部距离。
-   适配横屏、竖屏、沉浸式全屏和窗口变化。
-   只调整控制栏布局，不改变视频画面缩放。
-   退出全屏后恢复原有布局参数。

### 6.6 TabletDebugLogger

开发版本记录：

-   返回事件来源。
-   当前布局容器。
-   当前 Fragment 类型。
-   返回目标。
-   搜索状态保存/恢复过程。
-   系统 Insets 数值。
-   控制栏最终偏移量。

正式版本应可关闭详细日志，避免无必要的日志开销。

## 7. 功能一：平板返回导航优化

### 7.1 返回优先级

优化模式下建议按以下优先级处理，最终顺序须结合源码中实际存在的组件核验：

1.  当前全屏媒体查看器或播放器。
2.  当前显示的覆盖层、Sheet 或弹窗。
3.  当前 Fragment 自身可消费的内部状态。
4.  评论/讨论页面等上层 Fragment。
5.  搜索结果列表等父级 ChatActivity 内部状态。
6.  频道 ChatActivity。
7.  左侧聊天列表及主导航。

**重要：** 搜索结果属于父级 ChatActivity
的内部状态。只有评论页面关闭、父级页面重新成为当前页面后，才应恢复搜索结果；不能在评论页面仍显示时提前隐藏评论。

### 7.2 防止重复消费

每次 Back 事件应有明确的消费结果：

-   已由媒体查看器消费：不再关闭 Fragment。
-   已由覆盖层消费：不再继续返回。
-   已由当前 Fragment 内部状态消费：不关闭父页面。
-   已关闭一个 Fragment：不再继续处理同一次 Back。
-   无优化状态可处理：交给原有导航逻辑。

不能在同一次返回事件中连续执行多个 `finishFragment()`。

### 7.3 与原有导航栈协作

Telegram 已有多个 Fragment 栈。新导航模块不再维护完整页面栈，只记录原有
Fragment 栈无法表达的内部操作上下文。

页面的创建、销毁、转场和生命周期仍由原有 `ActionBarLayout` /
`BaseFragment` 体系管理。

## 8. 功能二：搜索与评论状态恢复

### 8.1 进入评论前保存状态

当用户从搜索结果打开消息评论时：

1.  判断当前是否为搜索结果列表。
2.  记录频道/会话标识。
3.  记录关键词及过滤条件。
4.  记录当前消息 ID。
5.  记录搜索列表滚动位置和偏移。
6.  记录搜索列表当前可见状态。
7.  关联即将打开的评论页面。

只有从搜索结果进入评论时才建立这份快照。普通频道消息打开评论不应产生无意义的搜索状态。

### 8.2 返回父级页面后恢复

1.  确认评论页面已经退出。
2.  确认恢复的是原始父级 ChatActivity。
3.  检查原搜索状态是否仍然有效。
4.  若原页面实例仍保留，优先恢复原实例。
5.  恢复搜索结果显示状态。
6.  等待 RecyclerView 完成布局后恢复消息位置。
7.  如消息 ID 已不存在，使用安全的备用位置。
8.  清除已消费的快照，避免下次返回重复恢复。

### 8.3 特殊场景

-   用户主动关闭搜索：不能在返回时强制重新打开。
-   搜索结果发生更新：优先按消息 ID 定位。
-   消息被删除：回退到可用的邻近位置或列表顶部。
-   切换频道：不得把旧频道的搜索状态恢复到新频道。
-   多次打开不同评论：每次上下文必须正确关联。
-   Activity/Fragment
    被系统回收：通过适当的实例状态保存机制恢复必要数据，不能依赖静态变量保存页面生命周期状态。

## 9. 功能三：全屏视频底部系统手势冲突修复

### 9.1 问题原理

Android
手势导航模式下，即使应用隐藏了系统导航栏，底部仍可能存在系统强制手势区域。

因此不能只根据 `navigationBars()` 或 `systemBars()` 判断底部是否安全。

### 9.2 Insets 读取

优先使用项目当前依赖支持的 `WindowInsetsCompat` API，读取：

-   `systemBars()`
-   `navigationBars()`
-   `systemGestures()`
-   `mandatorySystemGestures()`
-   必要时 `displayCutout()`

建议初始底部安全距离：

``` text
safeBottom =
    max(navigationBars.bottom,
        mandatorySystemGestures.bottom)

controlBottomMargin =
    safeBottom + extraSpacing
```

`extraSpacing` 初始建议 8dp，需实机验证。

不能把不同 Insets 简单相加，以免重复留白。

### 9.3 控制栏布局

只调整：

-   `videoPlayerControlFrameLayout`
-   `videoPreviewFrame`（如审计确认其确实需要同步调整）

不应直接给整个 `containerView` 增加底部
Padding，否则可能改变视频画面可用区域、宽高比和缩放。

### 9.4 进度条触摸区域

建议初始参数：

  项目                           建议
  ------------------ ----------------
  控制栏高度            保持原有 48dp
  进度条视觉高度         保持原有样式
  目标触摸高度            约 40--48dp
  额外底部安全间距           初始 8dp
  系统手势区域         不覆盖、不拦截

如果现有 48dp 控制栏已经提供足够触摸区域，优先不修改
`VideoPlayerSeekBar`。

### 9.5 系统手势保护

不得尝试通过 `setSystemGestureExclusionRects()` 禁用底部 Home / Quick
Switch 手势。该机制不能可靠地排除系统强制底部手势区域。

本项目采用：

**控制栏避让 + 安全区域内触摸热区 + 保留系统手势。**

### 9.6 横竖屏与窗口变化

Insets 必须动态更新，覆盖：

-   横屏全屏。
-   竖屏全屏。
-   隐藏/显示系统栏。
-   播放器窗口重新创建。
-   屏幕旋转。
-   分屏和自由窗口。
-   系统手势导航区域发生变化。

## 18. 最终技术决策

本项目采用以下方案作为正式开发方向：

1.  **增量改造，不复制整套平板源码。**
2.  **保留原有平板双栏布局和 Telegram Fragment 栈。**
3.  **增加独立的 Enhanced Tablet Mode 开关。**
4.  **统一优化模式下的平板返回事件分发。**
5.  **使用状态快照恢复搜索结果，而不是重新创建搜索页面。**
6.  **评论页面继续使用原有 ChatActivity 导航体系。**
7.  **PhotoViewer 读取底部强制系统手势 Insets，只调整媒体控制栏。**
8.  **不屏蔽 Android Home / Quick Switch 手势。**
9.  **手机模式和原版平板模式保持原样。**
10. **先固定 commit 并补全源码审计，再按 M1～M6 分阶段开发。**
